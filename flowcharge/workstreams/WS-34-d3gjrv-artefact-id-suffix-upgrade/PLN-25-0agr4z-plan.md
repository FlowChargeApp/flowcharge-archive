# Artefact ID suffix upgrade

## Summary

Praxis IDs now have the shape `TYPE-N-SUFFIX`, where `SUFFIX` is 6 random lowercase base-36
characters drawn at claim time. Six registered projects still carry the old suffix-less `TYPE-N`
form: Praxis-Board, LAD, DownloadAlbum, lad-poc, Praxis-Launch and Praxis-Demo. This plan
upgrades them.

The chosen approach is a single one-off Node script, `tools/migrate-artefact-ids.mjs`, run once
per project. It follows the exact shape the Praxis project's own completed migration proved out:
take a full backup, allocate the whole ID map first, write a plain mapping record, then rewrite
frontmatter, folder names and claim markers mechanically from that map. Free-text prose is never
rewritten automatically. The script instead emits a triage report of prose mentions for a human
to resolve one by one.

Reconnaissance found one thing the brief did not: this dashboard's own reader is not compatible
with the new ID shape. Three separate defects in `src/` silently drop or corrupt data for any
migrated project. They already affect Praxis and Praxis-Website today. Migrating six more
projects without fixing them first would blank the issue panels and scramble artefact ordering
across the whole board. Phase 1 fixes that compatibility gap before any data is touched.

## Scope

### Acceptance criteria

1. In each of the six target projects, every artefact `id:` frontmatter value matches
   `^(WS|PLN|IL|TL|ISS)-\d+-[0-9a-z]{6}$`.
2. Every `ISS-N` item id inside each `issuelist.md` carries a suffix, and the same id appears
   with the same suffix in every `issues:` frontmatter array that referenced it.
3. Every `workstream:`, `depends_on:`, `links:` and `issues:` frontmatter value that named an old
   id now names that id's mapped new value, with zero mismatches.
4. Every workstream folder is named `WS-N-SUFFIX-<slug>`, carrying the same suffix as the `id:`
   inside its own `workstream.md`.
5. Every old-format claim marker under `flowcharge/ids/` that corresponds to a mapped id is renamed
   to that new id.
6. `node <skills-dir>/prx-orchestrate/scripts/prx-index.mjs --root <project> --check` reports no
   new errors for each migrated project, compared to a baseline captured before migration.
7. A mapping record exists at `<project>/flowcharge/id-migration-2026-08-16.md`, listing every
   old id, its new id, every folder renamed and every claim marker renamed.
8. A full pre-migration copy of the project's `flowcharge/` tree exists at
   `<project>/flowcharge-pre-migration-2026-08-16/`.
9. This dashboard renders every migrated project's board with the same workstream count, issue
   count and artefact ordering it showed before that project was migrated.
10. `WS-34-d3gjrv` and its folder in this project are unchanged by the migration.
11. A prose-mention report exists per project, and every entry in it is either resolved or
    explicitly recorded as deliberately left alone.

### Out of scope

- The `Praxis` and `Praxis-Website` projects. Both are already migrated. Neither is read from or
  written to by the migration.
- Editing `Praxis-Website`'s source, including the `Hero.tsx` comment that cites `WS-31`. The
  handling for that is a findable mapping record, described in Design.
- Changing the shared `prx-orchestrate` skill, its `prx-index.mjs` script or its `CONVENTIONS.md`.
  Those belong to the `Praxis` project.
- Changing the format of `flowcharge/ids.md`. Its counters are bare numbers and stay bare numbers
  (finding 7).
- Regenerating or hand-editing `index.md` and `kanban.md` as content. They are generated
  views and are regenerated by the existing script.
- Creating claim markers that never existed, or deleting leaked ones. See Open questions 2.
- Any new dashboard feature. Phase 1 is compatibility repair only.

## Design

### The compatibility defects that must be fixed first

All three are in this project and all three are already live defects for Praxis and
Praxis-Website. They are verified, not suspected.

**1. The detail API rejects every new-format workstream.** `src/server.ts:262`:

```ts
if (!/^WS-\d+$/.test(wsId)) {
```

`WS-34-d3gjrv` fails this test, so `/api/projects/<id>/workstreams/<wsId>/detail` returns HTTP 400
for any migrated workstream. The guard exists to reject path traversal on shape, so the
replacement must stay a shape check, not become a filesystem check. The correct pattern is
`/^WS-\d+(-[0-9a-z]{6})?$/`, which keeps the traversal defence and accepts both forms.

**2. Every migrated issue is silently dropped.** `src/lib/extract.ts` matches issue items in three
places, all with the same assumption that a digit run is followed immediately by a period:

- line 53: `export const ISSUE_ITEM = /^-\s*\[([ xX])\]\s*(ISS-\d+)\.\s*(.*)$/;`
- line 130: `text.split(/\n(?=-\s*\[[ xX]\]\s*ISS-\d+\.)/)`
- line 132: `b.match(/-\s*\[([ xX])\]\s*(ISS-\d+)\.\s*(.*)/)`

Proven against the real migrated data: the pattern matches `- [x] ISS-2. …` and does not match
`- [x] ISS-18-awinon. …`, which is the live form in
`/Users/akoukoullis/Work/AK/Praxis/flowcharge/workstreams/*/issuelist.md`. There is no error. The
issues simply vanish from the board and from the severity panel. The comment above line 53 states
that the three patterns are deliberately character-identical in shape, so all three change
together or the modal and the board disagree.

**3. Artefact ordering is silently corrupted.** `src/lib/extract.ts:71`:

```ts
export function artefactIdNumber(id: string): number {
  const n = Number(id.slice(id.lastIndexOf('-') + 1));
  return Number.isFinite(n) ? n : 0;
}
```

It reads the number after the *final* hyphen, which under the new shape is the suffix. Verified
outputs: `TL-175` gives 175, `TL-175-ab12cd` gives 0, and `IL-9-000123` gives 123. The last case
is the dangerous one. An all-digit suffix produces a wrong but entirely plausible sort key, so the
ordering breaks without any visible fallback. This function is the whole mechanism behind
`WS-20-detail-modal-artefact-order-by-id`, and it is exported so `detail.ts` and the board share
one rule. The fix parses the number segment rather than the last segment.

What is **not** broken, and must stay that way: `locateWorkstream` in `src/lib/detail.ts:190`
resolves a workstream by scanning frontmatter `id:` values instead of joining the URL segment into
a path. It is shape-agnostic and already handles both forms. The client's dependency highlighting
in `src/public/app.ts` treats `depends_on` values as opaque strings compared against workstream
ids, so it is shape-agnostic too. Neither needs changing.

### The migration script

One file: `tools/migrate-artefact-ids.mjs`. It sits beside the existing `tools/copy-assets.mjs`,
following that convention rather than inventing a new location, and it keeps `flowcharge/` holding
artefacts only. It is a one-off, retained after the migration as the record of what ran.

**Interface.** Defined here so every phase builds against the same contract.

```
node tools/migrate-artefact-ids.mjs --root <project-root> [--dry-run] [--date <YYYY-MM-DD>]
```

- `--root` is required. The script refuses to run if `<root>/flowcharge/` is absent.
- `--dry-run` performs every read and every computation, writes the mapping record and the prose
  report to a temporary location, and makes no change inside `flowcharge/`. This is the default
  posture for first contact with any project.
- `--date` overrides the date stamp used for the backup folder and mapping record name. It exists
  so a resumed or repeated run reuses the original stamp rather than orphaning the first backup.

**Refusal conditions.** The script exits non-zero without writing when any hold:

- `<root>/flowcharge-pre-migration-<date>/` already exists and `--date` was not passed.
- The project has zero old-format artefacts. Praxis and Praxis-Website hit this, so pointing the
  script at an already-migrated project is a no-op refusal rather than damage.
- The finished map contains a duplicate new id.
- Any mapped folder rename would collide with an existing directory.

**Stages, in order.** This is the Praxis precedent's shape, made repeatable.

1. **Scan.** Walk `flowcharge/workstreams/` and `flowcharge/archive/`. Collect every artefact `id:`
   frontmatter value and every `ISS-N` item id inside every `issuelist.md`.
2. **Allocate.** For each collected old id matching `^(WS|PLN|IL|TL|ISS)-\d+$`, draw a suffix using
   the same algorithm as the live tooling: 6 characters from
   `'0123456789abcdefghijklmnopqrstuvwxyz'`, via `crypto.randomInt`. This mirrors `randomSuffix()`
   at `prx-index.mjs:64-69` rather than inventing a second algorithm. Ids that already match the
   new shape are skipped and never enter the map. That skip is what protects `WS-34-d3gjrv`.
3. **Assert.** Fail if the map has duplicate values, or if any old id appears twice.
4. **Back up.** Copy the whole `flowcharge/` tree to `flowcharge-pre-migration-<date>/`, matching the
   precedent at `/Users/akoukoullis/Work/AK/Praxis/flowcharge-pre-migration-2026-08-16/`.
5. **Write the mapping record** to `flowcharge/id-migration-<date>.md`, before any rewrite, so an
   interrupted run still leaves the map recoverable.
6. **Rewrite exact references.** Frontmatter keys only: `id:`, `workstream:`, `depends_on:`,
   `links:`, `issues:`, plus `ISS-N` item ids at the start of an issue-list checkbox line. These
   are structured data with a closed, known vocabulary per project, which is what makes mechanical
   rewriting safe here and unsafe in prose.
7. **Rename folders** to `WS-N-SUFFIX-<slug>`, derived from the mapped id and the existing slug.
8. **Rename claim markers** under `flowcharge/ids/` for every marker whose name is a mapped old id.
   Markers with no map entry are left alone and listed in the record.
9. **Emit the prose report** to `flowcharge/id-migration-<date>-prose-review.md`.

The script knows about markdown frontmatter, the id map and the filesystem. It must **not** know
anything about the dashboard's TypeScript, about which project it is running against, or about any
project's content. Every project-specific value arrives through `--root`.

### The mapping record

Format follows the precedent file at
`/Users/akoukoullis/Work/AK/Praxis/flowcharge/id-migration-2026-08-13.md`, which has four parts: a
header stating what the file is and why it is kept, an `| Old | New |` table, a list of workstream
folders renamed, and a list of claim markers retired. The header must repeat the precedent's key
sentence in substance: this is a plain record, nothing parses it, and it exists so a commit
message or review comment citing an old id can still be resolved.

For **Praxis-Launch only**, the record gains one extra section, `## Known external references`. It
names `Praxis-Website`'s `Hero.tsx` comment citing `WS-31` and gives that workstream's new id. This
is how the cross-repo coupling in finding 4 is discharged without editing `Praxis-Website`. A
second copy of that section goes into this workstream's folder as `cross-repo-references.md`, so
the other active session can find it from either side.

There is a related fact worth recording in that section. The `Praxis` migration deleted
`flowcharge/ids/WS-31`, `flowcharge/ids/PLN-23` and `flowcharge/ids/TL-25` as leaked claims. Those are
three of Praxis-Launch's four live artefact ids. Praxis-Launch's numbers therefore no longer have
protective markers in `Praxis`. The new suffix is precisely what makes that harmless going
forward, but the record should say so rather than leave it to be rediscovered.

### The prose report

The report lists every remaining occurrence of an old-shape id in file content that the exact-key
rewrite did not touch: artefact bodies, `gotcha` and `compatibility` fields, plan prose, task
descriptions. It never rewrites them. Finding 3 is the reason: the Praxis migration deliberately
left roughly 83 mentions alone because they cite another repository's ids or a superseded id that
should stay as historical text.

To make review tractable at LAD's scale, the report groups each occurrence into one of two
buckets, as a triage aid only. The final call on every entry stays human.

- **In-map.** The mentioned id is in this project's own map. Likely this project's own artefact,
  and a likely rewrite.
- **Not-in-map.** The mentioned id is not in this project's map. Likely a foreign project's id or
  an orphan. The default is to leave it alone.

Each entry carries file path, line number, the old id, the mapped new id where one exists, and the
surrounding line, so a reviewer decides without opening the file.

## Data & compatibility

**What changes on disk.** Frontmatter values, `ISS-N` item ids in issue lists, workstream folder
names, and claim-marker directory names. Nothing else. `ids.md` counters stay bare numbers.
`index.md` and `kanban.md` are generated views and are regenerated, not edited.

**Backward compatibility.** After Phase 1 the dashboard reads both shapes, so a half-migrated
estate renders correctly. That is what makes the one-project-at-a-time sequencing safe. The
shared `prx-index.mjs` already only recognises the new shape, so migration moves each project
towards the tooling rather than away from it.

**Rollback.** Per project, and the story differs by project because only three are git repos.

- Any project: delete `flowcharge/`, rename `flowcharge-pre-migration-2026-08-16/` back to `flowcharge/`.
  This is the only path for lad-poc, Praxis-Launch and Praxis-Demo, which is why the backup is a
  hard precondition rather than a convention.
- Praxis-Board, LAD, DownloadAlbum: `git checkout -- flowcharge/` also works, with the caveat that
  `flowcharge/ids/` is gitignored, per `GITIGNORE_TARGETS` at `prx-index.mjs:75`. Claim markers are
  therefore *not* restored by git and must come from the backup. Markers are ephemeral, so this is
  a low-severity gap, but it is the reason git alone is not sufficient even where it exists.
- Phase 1's dashboard fix is independently revertible and should not be reverted during a
  rollback. It is strictly additive: it widens patterns to accept both shapes.

**Point of no return.** There is none while backups are kept. Once the user deletes the
`flowcharge-pre-migration-2026-08-16/` folders, the non-git projects become unrecoverable. The plan
does not delete them.

**Ordering hazard.** Do not migrate a project while a `prx-*` skill session is claiming ids in it.
A claim landing mid-run would create a new-format id the map has never seen, and the folder rename
could collide. Each phase assumes exclusive access to its project.

## Testing strategy

The script is one-off, so coverage is proportionate: the pure logic gets real tests, the
filesystem effects are proven by dry-run and by the live verification gates in each phase.

- **Unit, Phase 1.** `artefactIdNumber` over both shapes, including the `IL-9-000123` case that
  currently returns a wrong-but-plausible 123. The three issue patterns over both item forms. The
  `server.ts` guard over `WS-5`, `WS-34-d3gjrv`, `../etc`, `WS-`, and `WS-5-ABC123`, so widening
  the pattern is shown not to have widened the traversal surface.
- **Unit, Phase 2.** Suffix generation shape and alphabet. Map construction, including the skip of
  already-new ids. The duplicate-map assertion. Frontmatter rewriting over each of the five keys,
  in both inline-array and scalar form. Folder-name derivation. The bucketing rule of the prose
  report.
- **Integration, Phase 2.** Run the script against a throwaway copy of a real project tree and
  diff the result against expectations. Assert idempotence: a second run refuses.
- **End-to-end, every migration phase.** `prx-index.mjs --check` against a baseline captured
  before the run, plus a board render comparison in the dashboard.

Phase 1's tests are the ones with lasting value. They guard a live defect and should stay in the
repository. The script's tests can retire with the script.

## Open questions

   estate-wide, and LAD dominates that. Options: (a) review every entry, which is honest but
   likely a day of judgment work on LAD alone; (b) review only the in-map bucket and record the
   not-in-map bucket as deliberately untouched; (c) skip LAD's prose entirely and keep only the

2. **What should happen to claim markers with no map entry?** The Praxis migration deleted six as

   destructive and the brief did not ask for it, and finding 5's warnings resolve on their own
   once scan-source detection sees the new ids. But the precedent chose (b), so this is genuinely
   the user's call.
3. **Should Phase 1 be its own workstream?** The three dashboard defects are pre-existing. They

   the board, so they are a genuine precondition. The alternative is to split them into their own
   bug-fix workstream and make this one depend on it. I recommend keeping them here, because the
   dependency is total and splitting adds a handoff for no benefit.
4. **Where should the backups end up once the migration is verified?** They are untracked
   directories inside three git repos and plain folders in three non-git projects. I did not plan
   their deletion, because deleting the only rollback path for three projects is not a decision
   this plan should make silently. The user decides when to remove them.

## Alternatives considered and rejected

**Manual per-file editing, as used by WS-30.** Rejected. WS-30 worked because it was a pure
rename with no minted values and no reference graph. This migration mints 1580 random values that
3127 other exact locations must agree on with zero tolerance for mismatch. LAD alone is 482 files.
The failure mode is one silent mismatch in a graph nobody re-reads, which is exactly what a script
prevents and a human does not.

**Blind find-and-replace across the whole `flowcharge/` tree.** Rejected, and the precedent is the
evidence. The Praxis migration deliberately left roughly 83 old-shape mentions untouched because
they cite another repository's ids or a superseded id that should remain historical text. A
sed-style sweep would silently rewrite those to point at the wrong artefact, and the damage would
be invisible because the result still looks well-formed.

**Adding a `--migrate-ids` flag to the shared `prx-index.mjs`.** Rejected on ownership and on
YAGNI. That script belongs to the `Praxis` project, which this workstream does not own, and it is
already the live claiming mechanism for every project. A one-off migration does not justify
permanently enlarging a shared tool that every project depends on. Verified that the script offers
no such flag today: its surface is `--check`, `--list`, `--claim`, `--sync`, `--new-ws`,
`--no-board`, `--whoami`.

**Migrating all six projects in one run.** Rejected. It removes every intermediate verification
gate and makes a single bad assumption cost six restores instead of one. Sequential runs cost a
few extra minutes and make each blast radius one project.

**Reusing `--claim` to mint each new id.** Rejected. `--claim` allocates the *next* number and
creates a marker, but this migration must keep each artefact's existing `N` and change only the
suffix. Using `--claim` would renumber everything, which the conventions forbid outright: ids are
never renumbered or reused. The script therefore reuses only `randomSuffix`'s algorithm, not the
claim path.

**Skipping the backup for the three git-backed projects.** Rejected. `flowcharge/ids/` is gitignored,
so git does not restore claim markers, and a uniform procedure across six projects is less
error-prone than one that varies by whether a project happens to have a git repository.

## Final summary

One one-off script, `tools/migrate-artefact-ids.mjs`, run once per project: back up, allocate the
whole map first, write a plain mapping record, rewrite frontmatter, folders and claim markers
mechanically, then hand prose mentions to a human as a triaged report.

Seven phases. Rough effort: one small phase to fix the dashboard, one large phase to build and
prove the script, four migration phases sized by project, one small close-out.

Top risks:

1. This dashboard cannot read the new ID shape today. Three verified defects in `src/server.ts`
   and `src/lib/extract.ts` drop issues and corrupt artefact ordering. Phase 1 must land first.
2. Three of six projects are not git repositories, so the pre-migration backup is the only
   rollback path and is a hard precondition.
3. Prose mentions cannot be rewritten mechanically, and LAD's volume makes exhaustive review
   expensive.

Needs your answer: how far to take LAD's prose review (question 1), and what to do with unmatched
claim markers (question 2). Questions 3 and 4 have working defaults and can ride as-is.
