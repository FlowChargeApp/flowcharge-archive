# Do not build bytenode compilation: record why and shelve the step

## Summary

This plan recommends **not building** the bytenode feature. It concludes the
workstream with a written decision record instead of code.

The workstream asked to compile the Electron main-process glue in
`dist/electron/` to V8 bytecode. This project's own investigation found that
only one of the three candidate files can be compiled at all. `main.cjs` and
`agentic-tools-ipc-handlers.cjs` both use a
`new Function('specifier', 'return import(specifier)')` bridge to load this
project's ESM code. bytenode runs compiled code through `vm.Script`
(`script.runInThisContext(...)`), which has no `importModuleDynamically`
callback, and the investigation confirmed empirically — against plain Node and
against this project's installed Electron 43.4.0 — that this throws
`ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING`. Adding the callback does not rescue
it; it then needs `--experimental-vm-modules` and fails differently.

That leaves `electron/ipc-handlers.cts` alone. Its compiled form is 3,842 bytes
of the three files' 25,610 bytes — 15.0%. Reading that file shows it holds no
secret: it is a relay with seven `ipcMain.handle` registrations and no
validation, no data model, and no business rule. Its comment header says so
directly ("No validation logic lives here"). Every channel name it registers is
also written in plain text in `electron/preload.cts`, which must ship readable
and unmodified. Every HTTP path it builds is visible in `dist/server.js`, which
ships as readable ESM and cannot be compiled under this feature's own settled
constraints.

So the achievable slice hides 3,842 bytes whose entire interface is already
disclosed by two other files in the same package. The cost is a first-ever
production dependency, a new build script that spawns Electron, a post-`tsc`
rewrite step, a separate compile pass per platform and per architecture, a
mandatory rebuild on every Electron upgrade, and a new uncatchable
`SIGTRAP`/`EXC_BREAKPOINT` crash class when bytecode and runtime ever
mismatch. The step was already ranked lowest-value and highest-effort of the
consultation's 11. The achievable slice is smaller than that ranking assumed,
while the cost is unchanged. The honest answer is to stop.

**Chosen approach: path (b) — recommend against the feature and record why.**
Path (a), the partial implementation of `ipc-handlers.cjs` only, is designed in
full under "Alternatives considered and rejected" so a future reader can see
exactly what was declined and can pick it up if the trade-off ever changes.

### Assumptions

These are assumptions, not confirmed decisions. Each one is stated because the
plan was written without a user available to answer.

- **A1.** The purpose of the parent consultation is to raise an attacker's cost,
  not to create a security boundary. The consultation framed itself that way
  throughout. This plan therefore judges the feature on cost-versus-benefit, not
  on whether it is a control that must exist.
- **A2.** The packaged app has no live users and no production data to protect,
  because the README states the builds are unsigned, unnotarized, and intended
  for the author's own machine. A "do not build" outcome therefore carries no
  release risk and needs no flag, no dark launch, and no rollback path.
- **A3.** The 15% figure is measured from the current `dist/electron/` output
  and will drift as the source changes. It is a snapshot for this decision, not
  a tracked metric.
- **A4.** No external requirement — customer, contract, audit, or store policy —
  demands that main-process code be non-readable. If one existed, the answer
  would change, because then the question becomes compliance rather than value.
  See Open questions Q1.
- **A5.** The single-file compile shape described in path (a) below would work
  as investigated. It is not tested here, because the recommendation is not to
  build it. Anyone reviving path (a) must verify it rather than trust this plan.

## Design

The deliverable is a decision, so this section records the technical shape of
the decision rather than a module design.

### What exists today

`electron/tsconfig.json` compiles exactly four files into `dist/electron/`:

| Source | Compiled | Size | Role |
|---|---|---|---|
| `electron/main.cts` | `main.cjs` | 5,130 B | main process, the `package.json` `"main"` entry |
| `electron/ipc-handlers.cts` | `ipc-handlers.cjs` | 3,842 B | IPC relay to the loopback HTTP server |
| `electron/agentic-tools-ipc-handlers.cts` | `agentic-tools-ipc-handlers.cjs` | 16,638 B | IPC handlers for the agentic-tools install flow |
| `electron/preload.cts` | `preload.cjs` | 2,058 B | sandboxed preload, excluded from this feature |

The three candidate files total 25,610 B.

### The blocking fact

`electron/main.cts:65-67` builds the bridge:

```ts
const dynamicImport = new Function('specifier', 'return import(specifier)') as (
  specifier: string
) => Promise<unknown>;
```

`main.cts:70` uses it to load `../server.js` — that call starts the entire HTTP
server, and `main.cts:79` awaits the port the server reports. Without it the app
has no server and no window.

`electron/agentic-tools-ipc-handlers.cts:237` builds the same bridge, and lines
317-344 use it to load nine library modules from `dist/lib/`.

The bridge exists because `require()` cannot load ESM, and TypeScript's
CommonJS output rewrites a literal `import()` into
`Promise.resolve().then(() => require(...))`, which throws `ERR_REQUIRE_ESM`
against `dist/server.js`. The `main.cts` comment at lines 39-47 records this.
The root `package.json` sets `"type": "module"`, so `dist/server.js` and
`dist/lib/*` are ESM and will stay ESM — converting them is settled as rejected.

bytenode executes compiled bytecode through `vm.Script`. A `vm.Script` created
without an `importModuleDynamically` callback throws
`ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING` on any dynamic import inside it. The
investigation verified this against plain Node and against this project's own
Electron 43.4.0 binary. Supplying the callback moves the failure rather than
removing it: it then requires `--experimental-vm-modules`.

Therefore `main.cjs` and `agentic-tools-ipc-handlers.cjs` — 21,768 B, 85.0% of
the candidate code — cannot be compiled without first replacing the bridge, and
the investigation found no obvious replacement.

### Why the remaining 15% is not worth taking

`electron/ipc-handlers.cts` is 109 lines. It contains one `http.request` helper
and seven `ipcMain.handle` registrations. Its own header comment states that no
validation logic lives there and that every rule keeps running inside
`src/server.ts`.

Its full interface is already readable elsewhere in the same shipped package:

- All seven channel names — `listProjects`, `addProject`, `renameProject`,
  `removeProject`, `getProjectData`, `getWorkstreamDetail`,
  `pickProjectFolder` — are written in plain text in
  `electron/preload.cts:11-18`, which ships as readable `preload.cjs` and must
  not be touched.
- The HTTP paths it builds — `/api/projects`,
  `/api/projects/:id/data`, `/api/projects/:id/workstreams/:wsId/detail` — are
  written in plain text in `dist/server.js`, which ships readable and is out of
  scope for compilation by settled constraint. They are also visible to anyone
  watching the app's own loopback traffic.

An attacker who wants to know what this file does reads `preload.cjs` and
`server.js` and learns everything, whether or not `ipc-handlers.jsc` exists.

### What the 15% would cost

- **A first production dependency.** The packaged asar has no `node_modules`
  folder today, because the project has zero production dependencies. The README
  states "no runtime dependency, no framework and no bundler". Adding `bytenode`
  to `dependencies` — mandatory, because electron-builder copies production
  `node_modules` but never dev dependencies — ends that property permanently, to
  protect a relay file.
- **A new build stage.** A script calling `compileFile({ electronMain: true })`,
  which spawns a real Electron browser process to compile. The bytenode CLI
  cannot be used: it has no `electronMain` flag. `ELECTRON_RUN_AS_NODE=1` cannot
  be used: it hard-crashes with `SIGTRAP` on Electron 43.4.0.
- **A post-`tsc` source rewrite.** `dist/electron/main.cjs:15` emits
  `require("./ipc-handlers.cjs")` with an explicit extension. That specifier
  must be rewritten to `"./ipc-handlers.jsc"` after every build, and a
  `require('bytenode')` must run before it to register the `.jsc` extension
  hook.
- **A packaging change per target.** `"!dist/electron/ipc-handlers.cjs"` added
  to `build.files`, named individually rather than by wildcard so `preload.cjs`
  and `main.cjs` are never caught.
- **Three CI shapes that cannot share output.** No cross-compiling.
  `package:mac` needs x64 and arm64 passes, `package:linux` needs its own runner
  with `xvfb-run`, `package:win` needs its own. Each needs Electron installed to
  compile.
- **A rebuild obligation on every Electron upgrade**, forever.
- **A new uncatchable crash class.** A `.jsc` run under the wrong V8 either
  throws a catchable `cachedDataRejected` or hard-crashes with
  `EXC_BREAKPOINT`/`SIGTRAP` with no catchable error. The second case is the
  dangerous one, and it is a process-type checksum mismatch, so it is exactly
  the case a packaging mistake produces.
- **A live arrow-function risk, not a footnote.** bytenode's own Known Issues
  document arrow functions as a crash risk, because V8 inspects them with
  `Function.prototype.toString` across context changes.
  `electron/ipc-handlers.cts` contains 12 arrow functions in 109 lines. All
  seven `ipcMain.handle` callbacks are arrows, as are all four `res.on`/`req.on`
  callbacks inside `loopbackRequest`. This file is arrow-function-dense, so the
  one file that can be compiled is also the one most exposed to bytenode's own
  documented failure mode.

### The decision

Do not build it. Close the workstream as `dropped`, keep this plan as the
record, and treat the bridge-replacement work as a separate, unauthorised idea
rather than a queued task.

## Data & compatibility

Nothing to migrate. No data model, no stored file, no API contract, and no
on-disk format changes. `.praxis-projects.json` and `PRAXIS_DATA_DIR` are
untouched.

Backward compatibility is total, because the packaged app is byte-identical to
today's. The build output, the asar contents, and the three `package:*` scripts
all stay as they are.

The rollback story is trivial: the only artefacts are markdown files under
`flowcharge/`. Reverting the commit restores the workstream to `backlog`. No
released build is affected, because none is produced.

This is itself part of the argument for the decision. Path (a) would have had a
real compatibility surface — a version-locked binary in the package, a per-arch
build matrix, and a hard-crash failure mode — for a file that carries no data
and no contract.

## Testing strategy

No application code changes, so there are no unit or integration tests to
write. This section instead records what a later test-writing pass would have to
cover if path (a) were ever revived, so the cost is not rediscovered.

- **Phase 1-3 verification** is the commands listed per phase above. It is
  document and build-output checking, not test authoring.
- **Regression guard:** `npm run build` followed by `npm run electron:dev` must
  open the board and list projects. This proves the workstream changed nothing.
  It is a manual check, matching how the Electron shell is already exercised in
  this project.
- **If path (a) is ever revived**, the test burden would include: a launch test
  of the packaged app on each of macOS x64, macOS arm64, Linux x64, and Windows
  x64, because bytecode failures are platform-specific and one of the two
  failure modes is an uncatchable crash; an exercise of all seven IPC channels
  through the real UI, because the arrow-function risk shows at call time and
  not at load time; and a deliberate mismatch test that runs a `.jsc` under a
  different Electron build, to learn which of the two failure modes this project
  actually gets. That burden is per release, per platform, forever. It is a
  large part of why the recommendation is to decline.

## Alternatives considered and rejected

### Path (a) — compile only `ipc-handlers.cjs` (rejected, but designed here)

The one shape that is technically achievable today. Recorded in full so nobody
has to re-derive it.

The build would add `bytenode` to `dependencies` — not `devDependencies`,
because electron-builder copies production `node_modules` into the packaged app
and never dev dependencies, and this project's asar has no `node_modules` at
all today. A build script would call `compileFile({ electronMain: true })` from
bytenode's JS API after `tsc`, never the CLI (no `electronMain` flag) and never
`ELECTRON_RUN_AS_NODE=1` (hard `SIGTRAP` on Electron 43.4.0). The script would
then rewrite `require("./ipc-handlers.cjs")` to `require("./ipc-handlers.jsc")`
in `dist/electron/main.cjs`, and a `require('bytenode')` line would be added
near the top of `electron/main.cts` if `main.cjs` does not already serve as the
loader point. The require cycle between the two files stays safe here precisely
because only one side of it changes format. `package.json`'s `build.files` would
gain `"!dist/electron/ipc-handlers.cjs"`, named individually so `preload.cjs`
and `main.cjs` are never caught by a wildcard. Each of `package:mac` (x64 and
arm64), `package:linux` (with `xvfb-run`) and `package:win` would need its own
compile pass on its own runner.

**Rejected because** the benefit is 15.0% of the candidate code, and that 15% is
a relay whose entire interface is already plain text in `preload.cjs` and
`dist/server.js`, both of which must keep shipping readable. Against that, the
cost is permanent: the project's first production dependency, a per-platform
build matrix, a rebuild obligation on every Electron upgrade, an uncatchable
`SIGTRAP` failure mode, and bytenode's own documented arrow-function crash risk
landing on the single most arrow-dense file in `electron/` (12 arrows in 109
lines). The step was already ranked lowest-value and highest-effort of 11 when
it was assumed to cover all three files. At 15% coverage of the least valuable
code, the ranking's own logic points at dropping it.

### Path (a-extended) — replace the dynamic-import bridge, then compile all three

Would restore the feature's full intended coverage by removing the blocker.

**Rejected because** it is a materially different and much larger piece of work
than this consultation ever scoped, and it is riskier. The bridge in
`main.cts:65-67` is what starts the HTTP server, and the bridge in
`agentic-tools-ipc-handlers.cts:237` loads nine library modules. The
investigation found no obvious replacement, and the two obvious ones are both
closed: converting `src/server.ts` and `src/lib/` to CommonJS is settled as
rejected by the parent consultation, and `--experimental-vm-modules` is not
something to ship in a packaged desktop app. Rebuilding load-bearing startup
code so that a hardening step ranked last of 11 becomes possible is the wrong
order of priorities. If this is ever wanted, it is a separate workstream that
must be justified on its own, and it is the strict precondition for reviving
path (a) at full coverage.

### Do nothing and leave the workstream in `backlog` (rejected)

Cheapest in the moment.

**Rejected because** it leaves a card on the board that reads as pending work,
while the analysis showing it should not be built stays only in a consultation
transcript. The next person to look at the board would repeat this
investigation. A `dropped` workstream with this plan attached costs the same and
keeps the answer.

## What should happen instead

Shelve the idea. Set WS-64 to `dropped`, keep `PLN-54-kcr1ok` as the record, and
do not create a follow-up workstream unless the user asks for one (Open question
2).

The precondition for revisiting is explicit: **the dynamic-import bridge in
`electron/main.cts` and `electron/agentic-tools-ipc-handlers.cts` must be gone,
replaced by something that runs inside `vm.Script`.** Until then, the achievable
coverage stays at 15% of glue code that is already disclosed elsewhere in the
package, and the cost-versus-benefit does not change. If that bridge is ever
removed for an unrelated reason, this plan is the place to start re-evaluating.

Attention is better spent on the other ten steps of the source-hardening
consultation, all of which were ranked above this one, and none of which carry
an uncatchable-crash failure mode.

## Final summary

- **Chosen approach:** do not build the feature; close WS-64 as `dropped` and
  keep this plan as the decision record.
- **Phases:** 3, all documentation and verification. Total effort: small.
- **Why:** 85% of the target code cannot be compiled at all, because of a
  `vm.Script` dynamic-import limitation confirmed against Electron 43.4.0. The
  remaining 15% is a relay whose channel names and HTTP paths already ship in
  plain text in `preload.cjs` and `dist/server.js`.
- **Top risks of building it anyway:** an uncatchable `SIGTRAP` crash on any
  bytecode/runtime mismatch; bytenode's documented arrow-function crash risk on
  the most arrow-dense file in `electron/`; a permanent per-platform,
  per-upgrade rebuild obligation and the project's first production dependency.
- **Needs your answer:** Q1, whether any external requirement forces this (the
  recommendation assumes not); Q2, whether to record the bridge-replacement work
  as a future workstream (recommendation: no); Q3, whether the parent
  consultation document should be updated; Q4, whether the "raise the cost, not
  a boundary" framing still holds.
