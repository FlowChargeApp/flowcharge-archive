# Read the FlowCharge tree names, with a warned legacy fallback

## Summary

The upstream FlowCharge suite renames a project's data folder from `prxwork/` to
`flowcharge/` and drops the `prx` prefix from the workstream marker file
(`prxworkstream.md` → `workstream.md`). This Dashboard locates and parses that tree in
four places, so the rename makes every registered project unreadable.

The chosen approach adds one small resolution module, `src/lib/tree-layout.ts`, that owns
both name generations. It resolves `flowcharge/` first and falls back to `prxwork/`, and
it accepts either marker filename inside whichever folder resolved. Every read site calls
it instead of holding a literal. The fallback is a **warned compatibility window**, not a
silent one: a resolution through the legacy names logs one deprecation line naming the
project path, which is the observable signal that later authorises the fallback's removal.

Two reconnaissance findings shape this. First, the per-file prefixes (`prxplan.md`,
`prxissuelist.md`, `prxtasklist.md`) and the root-level files (`prxindex.md`,
`prxkanban.md`, `prxids.md`, `prxtags.md`, `prxagents.md`, `.prxlease`) need **no code
change at all** — both parsers already key on frontmatter `type`, never on those
filenames, and the walk never descends to the tree root. The real coupling is two names,
not eleven. Second, the compatibility question is not hypothetical scheduling: it decides
whether an older git checkout or worktree of a project stays readable.

## Scope

### Acceptance criteria

1. A registered project whose data folder is `flowcharge/` and whose workstream folders
   hold `workstream.md` renders a full board: every workstream appears as a card, with its
   plan, issue-list and task-list artefact rows.
2. That same project's card modal opens and populates its plan, issues and tasks tabs.
3. A registered project whose data folder is still `prxwork/` and whose workstream folders
   hold `prxworkstream.md` renders exactly as it does today, with no user-visible
   difference except a deprecation warning in the server log.
4. Every legacy resolution logs exactly one deprecation line, naming the resolved
   absolute path and the folder name it should take.
5. A project directory holding a `prxwork-bak/`, `prxwork-pre-migration-<date>/` or any
   other name-adjacent sibling directory does **not** resolve through it. Only the exact
   basenames `flowcharge` and `prxwork` resolve.
6. A project holding both `flowcharge/` and `prxwork/` resolves through `flowcharge/`, and
   logs no deprecation warning.
7. A workstream folder holding the marker of the other generation than its parent folder
   suggests — `flowcharge/…/prxworkstream.md`, or `prxwork/…/workstream.md` — is still
   found, not silently skipped.
8. Neither marker filename ever appears as an artefact row on a card or as an entry in the
   modal's plan, issue-list or task-list collections.
9. `POST /api/projects` rejects a directory holding neither folder, with a message naming
   `flowcharge/` as the folder to create.
10. `npm run build` completes with no TypeScript error, and
    `node --test dist/lib/tree-layout.test.js dist/lib/extract.test.js dist/lib/detail.test.js`
    passes. The whole-suite `node --test dist/lib/*.test.js` is **not** the gate: it fails
    today on the pre-existing old-skill-id coupling that Open question 2 describes, which
    this workstream does not touch. See Testing strategy.

### Assumptions

These were settled without the user, and each is stated so it can be overturned cheaply.

- **A1 — the interior shape is unchanged.** Only the outer folder name and the marker
  filename move. `workstreams/` and `archive/` keep their names inside the tree. Confirmed
  against the "Layout — workstream folders, not date buckets" section of
  `~/.claude/skills/fc-orchestrate/CONVENTIONS.md`, whose tree diagram shows
  `flowcharge/workstreams/` and `flowcharge/archive/` unchanged, and against ten live trees
  on this machine. Cited by section rather than by line, because that file is edited
  upstream and its line numbers move.
- **A2 — deployment constraints.** The runtime is a single-user local application: a Node
  server on `127.0.0.1`. The packaging is not casual, though. `package.json` configures
  electron-builder for macOS (`dmg` and `zip`, x64 and arm64) with `hardenedRuntime: true`
  and `notarize: true`, for Windows (`nsis`, x64 and arm64) with the DigiCert RFC 3161
  timestamp server, and for Linux (`deb`, `AppImage`), and it declares a GitHub `publish`
  block with `releaseType: draft` and `publishAutoUpdate: true`. So a shipped build is
  signed, notarized and auto-updating, not an unsigned local binary. Two things follow.
  First, there is still no production **data** and no live user, so a feature flag remains
  unwarranted and the app need only stay runnable at every commit. Second, the release
  path is a real gate: this change must land before a build is cut, not after. Note the
  `publish` block still carries `TODO-REPLACE-OWNER` / `TODO-REPLACE-REPO`, so no release
  has actually gone out from this configuration yet.
- **A3 — the breakage is live, not imminent.** Context asked for the rename to be treated
  as not yet landed. Reconnaissance contradicts this on this machine: all ten projects in
  `.praxis-projects.json` already hold `flowcharge/` with `workstream.md`, and **none**
  holds `prxwork/`. Every board is broken today. This changes urgency, not design.
- **A4 — the legacy fallback still earns its place.** With zero legacy trees registered, a
  hard cutover is tempting. It is rejected because the Dashboard reads projects by absolute
  path, so a git worktree or an older checkout of any of those ten projects presents the
  old layout, and because Context states registered projects migrate independently.
- **A5 — the registry needs no migration.** `.praxis-projects.json` stores an id, a display
  name, an absolute project root and a date. Verified against all ten live entries: no
  stored path carries a `prxwork` segment, and no config key is named for it.
  `src/lib/projects.ts` hashes the project root only (`projectId`, line 26).

## Design

### Where the coupling actually is

Four literal-holding sites, and only two distinct names between them:

| Site | Line | Literal |
|---|---|---|
| `src/lib/extract.ts` | 204, 213 | `'prxwork'` |
| `src/lib/extract.ts` | 124, 133 | `'prxworkstream.md'` |
| `src/lib/detail.ts` | 206 | `'prxwork'` |
| `src/lib/detail.ts` | 195, 221 | `'prxworkstream.md'` |

`src/server.ts:6` imports `hasPrxwork` and calls it at three route boundaries — the
add-project guard at line 197, the board-data guard at line 335 and the detail guard at
line 369. Each guard is followed on the next line by a user-facing message naming
`prxwork/`: lines 198, 336 and 370. Calls and messages are one line apart, so both sets
need editing.

Everything else in the tree is already name-agnostic and must stay untouched:

- **Artefact filenames need no change.** `src/lib/extract.ts:138-140` keys on frontmatter
  `id` and `type`; `src/lib/detail.ts:227-228` states outright that "Frontmatter `type` is
  the sole source of truth — Filename is ordering and display only." Dropping the `prx`
  prefix from `prxplan.md` therefore costs zero lines.
- **Root-level files are never read.** The walks enter `<tree>/workstreams` and
  `<tree>/archive` only (`extract.ts:216-217`, `detail.ts:209-210`), so `index.md`,
  `kanban.md`, `ids.md`, `tags.md`, `agents.md` and `.lease` are out of reach by
  construction. A grep for those tokens across `src/` returns nothing.
- **Artefact IDs are unchanged** by the upstream rename, so `ID_SUFFIX`,
  `artefactIdNumber`, `ISSUE_ITEM` and `TASK_ITEM` (`extract.ts:56-91`) are not touched.

### The new module: `src/lib/tree-layout.ts`

A new single-concern library file, matching the shape this repo already uses for
`git.ts` (40 lines), `yaml-block.ts` and `projects.ts`. It is a new module rather than an
addition to `extract.ts` because `extract.ts` declares itself the board-payload extractor,
while three separate consumers — `extract.ts`, `detail.ts` and `server.ts` — need name
resolution.

The contract, fixed here before any phase depends on it:

```ts
export type LayoutGeneration = 'flowcharge' | 'prxwork';

export interface TreeLayout {
  dir: string;                 // absolute path of the resolved data folder
  generation: LayoutGeneration;
  legacy: boolean;             // true only when generation === 'prxwork'
}

// Resolves <root>/flowcharge first, then <root>/prxwork. null when neither is a
// directory. Never throws.
export function resolveTreeLayout(root: string): TreeLayout | null;

// True when either generation resolves. Replaces extract.ts's hasPrxwork.
export function hasWorkstreamTree(root: string): boolean;

// True when `file` is the workstream-folder marker of EITHER generation.
export function isWorkstreamMarker(file: string): boolean;

// The marker filenames, new generation first. Exported for the two locate walks.
export const WORKSTREAM_MARKERS: readonly string[];
```

What this module knows: two folder basenames, two marker basenames, and which is newer.
What it must **not** know: frontmatter, artefact types, HTTP, the registry, the board
payload, or `console`. It returns facts; the caller decides what to print.

### Four decisions the contract encodes

1. **Exact basename matching, never a prefix or a glob.** `fs.existsSync(path.join(root,
   'flowcharge'))` and the same for `prxwork`, plus an `isDirectory()` check. This is
   load-bearing, not defensive: the live trees on this machine hold `prxwork-bak/`,
   `prxwork-pre-crossref-2026-08-17/` and `prxwork-pre-migration-2026-08-17/` as siblings.
   A prefix match would resolve a stale backup and render a board from months-old data with
   no error at all. Acceptance criterion 5 guards this.

2. **`flowcharge/` wins when both exist.** During a migration the new tree is the live one
   and the old one is the leftover. Reading both and merging is rejected below — it would
   double every card.

3. **Marker acceptance is loose, not paired to the resolved folder.** A `flowcharge/` tree
   whose folders still hold `prxworkstream.md` is read, and the reverse too. The reason is
   the failure mode: a folder whose marker is not recognised is skipped with **no error and
   no log** (`extract.ts:125`, `detail.ts:196` both `continue`). A half-renamed tree would
   lose cards silently. Loose acceptance costs one extra string comparison and converts
   silent data loss into a correct read.

4. **Both markers are skipped in the artefact loop.** `extract.ts:133` and `detail.ts:221`
   currently skip one filename. If they skipped only the resolved generation's marker, the
   other marker file would be read as an artefact — it carries `id` and `type: workstream`
   in its frontmatter, so `extract.ts:138` would accept it and push a phantom row onto the
   card, sorted into the `UNRANKED_TYPE` bucket. `isWorkstreamMarker` is the single
   predicate used at all four sites, so the skip and the locate can never disagree.

### The deprecation warning

`resolveTreeLayout` returns `legacy: true`; it does not print. The printing lives at the
transport boundary in `src/server.ts`, which is the layer that already owns
`console.warn` for the non-loopback bind (`server.ts:465-474`) and already owns every
user-facing message about a missing folder. One line per resolution, carrying a fixed,
greppable marker so the user can observe whether the fallback is still load-bearing:

```
LEGACY LAYOUT: <path> uses prxwork/ — rename it to flowcharge/; support for the old name will be removed
```

The `--refresh` CLI (`src/scripts/extract-praxis-data.ts`) is the second entry point and
prints the same line, for the same reason.

### User-facing copy

Twelve strings name the old folder or the old artefact filenames to the user, and they are
part of this resolution layer's visible contract rather than incidental prose. They split
across two phases, and the split is not negotiable:

- **Phase 3 owns the three server strings** — `src/server.ts:198, 336, 370`. They are
  rewritten in the same edit that migrates the guards above them, because the message and
  its guard are one line apart and splitting them across phases would leave a route
  answering with the wrong folder name. Phase 4 does **not** touch `src/server.ts`.
- **Phase 4 owns the nine browser-bundle strings** — `src/public/home.ts:155, 311`,
  `src/public/index.html:46, 47`, `src/public/board.html:71, 90`, and
  `src/public/app.ts:810, 825, 887`. These move after behaviour is correct.

`src/public/index.html:48` is deliberately excluded: it names `.praxis-projects.json`,
which this workstream does not rename.

## Data & compatibility

- **No migration.** Nothing is written into any scanned project. The Dashboard's read-only
  posture is stated at `src/lib/projects.ts:102-104` and enforced by there being no write
  path. `src/lib/extract.ts:1-3` makes a different claim — that the library knows nothing
  about argv, stdout or HTTP — which supports the module boundary in Alternatives, not the
  read-only posture.
- **No registry change.** Per assumption A5, `.praxis-projects.json` carries absolute
  project roots only. Existing entries keep working across the change with no rewrite, and
  their ids stay stable because `projectId` hashes the path alone.
- **Backward compatibility with old trees** is the deliverable, not a side effect: a
  `prxwork/` project keeps rendering identically, gaining only a log line.
- **Forward compatibility** for a half-migrated tree is covered by decision 3 — either
  marker is accepted in either folder.
- **What breaks anyway.** A project holding neither folder is rejected at the add boundary
  and returns `410` on an existing entry. That is today's behaviour, unchanged.
- **Rollback.** `git revert` of the phase commits plus `npm run build`. There is no state
  to unwind. Reversible at every phase, with two caveats. First, after Phase 3 deletes the
  `hasPrxwork` re-export, reverting Phase 1 alone will not compile — revert Phase 3 first.
  Second, per assumption A2, a revert is only cheap while the change is unreleased: once a
  signed and notarized desktop build carrying it has shipped, rolling back means cutting
  and publishing a new build, because `publishAutoUpdate` is on. Land this before a build
  is cut.
- **Removal of the legacy branch** is deliberately *not* scheduled here. The
  `LEGACY LAYOUT:` line is the signal: when no registered project has produced it for a
  period the user judges long enough, deleting `'prxwork'` and `'prxworkstream.md'` from
  `tree-layout.ts` is a single-file follow-up. See Open question 1.

The verify gate is `npm run build`. There is no test runner script; existing tests run ad
hoc, as `src/lib/extract.test.ts:8` documents. Every phase below ends with
`npm run build` followed by a `node --test` run over the three test files this workstream

## Alternatives considered and rejected

- **New names only, hard cutover.** Delete the two old literals and be done. Rejected
  because the Dashboard resolves projects by absolute path, so a git worktree or an older
  checkout of any registered project still presents `prxwork/`, and because Context states
  that registered projects migrate independently. The cutover also converts a working board
  into a `410` with no explanation of why yesterday's project stopped existing. The saving
  is roughly ten lines.
- **Refuse a legacy tree with a clear error, rather than reading it.** A middle path:
  detect `prxwork/` and return a `410` naming the rename. Rejected because it is strictly
  worse than reading it — the same detection code, the same maintenance, but the user
  cannot see their board.
- **A configurable folder name per registry entry.** A `layout` or `dataDir` key in
  `.praxis-projects.json`. Rejected as gold-plating against YAGNI: two names exist, one is
  replacing the other, and the resolver settles it with no configuration and no migration
  of ten existing registry rows.
- **Prefix or glob directory matching**, so `prxwork*` or `*work*` resolves. Rejected
  outright and named in the tests: it would resolve `prxwork-bak/` and
  `prxwork-pre-migration-2026-08-17/`, which exist right now, and render a board from stale
  data with no error.
- **Strict pairing of folder generation to marker generation.** Simpler to state, and
  correct for an atomic upstream rename. Rejected because a half-renamed tree then loses
  cards with no error, no log and no exception — the worst failure mode available here —
  and the loose form costs one string comparison.
- **Reading both trees and merging when both exist.** Rejected: workstream ids are stable
  across the rename, so every card would appear twice, and the board has no deduplication
  layer to add one to.
- **Putting the resolver inside `extract.ts`.** Fewer files, and `detail.ts` already
  imports from it (`detail.ts:9`). Rejected because `server.ts` would then import path
  resolution from the board extractor, and `extract.ts:1-3` declares a narrower job than
  that. A 40-line single-concern library matches `git.ts` and `yaml-block.ts`.
